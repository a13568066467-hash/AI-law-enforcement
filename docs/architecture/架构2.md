## 30 秒开场（可直接念）

我们在 DSJ 执法仪上做了 **赢筑AI 主控 App**，配套 **手机扫码 App（`mobile-app`）** 完成公司设备池临时绑定；云端 **FastAPI + MySQL** 接 **百炼 AI** 做对话和识图。V1 的录像、拍照、扫码绑定已稳定。V2 正在做远程视频：设计上 **单路 H.264 编码同时写 MP4 和推流**，支持 **GB28181 国标** 和 **WebRTC 专家连线**。目前 **HTTP 信令 + JPEG 预览** 已从 Web 打到设备并在大屏显示，推流不影响本地录制和侧键。下一步是启用 MediaCodec 管线、接真 WebRTC 和 GB28181，完成 **30 分钟推流 + 录制并存** 验收。

## 7. V2 视频通信 — 目标架构



### 7.1 核心约束（PRD 硬要求）

> **推流期间本机 1080p H.264 录制不能中断。**



### 7.2 单编码器 + 双输出（设计关键）

```
Camera2 (YUV)
    ▼
MediaCodec (H.264 1080p 30fps 8Mbps)
    ├──► MediaMuxer ──► MP4（本机录制，格式不变）
    └──► NAL 队列
              ├──► GB28181 SIP UA ──► 国标平台（RTP/UDP）
              └──► WebRTC PeerConnection ──► 浏览器（SRTP）
```

V1 的 `MediaRecorder` 是黑盒，无法抽 H.264 码流；V2 用 `MediaCodec + MediaMuxer` 替换，对外 API 尽量不变。

### 7.3 两种推流场景


| 场景     | 协议          | 远端              | 延迟目标    |
| ------ | ----------- | --------------- | ------- |
| 专家远程连线 | **WebRTC**  | 指挥中心 Web        | ≤ 500ms |
| 平台级监控  | **GB28181** | 海康/大华等国标 SIP 平台 | ≤ 2s    |




### 7.4 八个实施模块（M1–M8）


| #   | 模块                           | 状态（2026-07-10）                   |
| --- | ---------------------------- | -------------------------------- |
| M1  | MediaEncoderPipeline         | 🟡 代码完成，**默认未启用**                |
| M2  | SipUaClient (GB28181)        | 🟡 代码完成，未自动注册/接线                 |
| M3  | WebRtcPeer                   | 🟡 信令框架，**无 google-webrtc 媒体通道** |
| M4  | MqttTopicRouter WebRTC Topic | 🟢 Topic 已加，与 HTTP 信令并行          |
| M5  | VideoStreamManager           | 🟡 NAL 分发框架，消费者待接真 RTP           |
| M6  | SessionManager 扩展            | 🟢 预览推流、设备 poll、Web 联动           |
| M7  | PTT 对讲                       | 🟡 视频通话分支存在，音频通道未完成              |
| M8  | StreamingPipelineWatchdog    | 🟡 仅 NAL 模式                      |

## 8. 当前已跑通链路（可现场演示）

**AI-screen ↔ text1 backend ↔ 设备** 的 **JPEG 预览** 端到端：

```
Web/AI-screen                    backend                         设备 App
    │                                │                                │
    │ POST /v1/webrtc/call/start     │                                │
    │ ─────────────────────────────► │                                │
    │                                │  GET /device/{id}/poll         │
    │                                │ ◄─────────────────────────────── │
    │                                │  返回 call_start               │
    │                                │                                │
    │                                │  设备自动开录 + JPEG POST      │
    │                                │ ◄── /call/{id}/frame ──────────│
    │ GET /call/{id}/frame           │                                │
    │ ◄──────────────────────────────│                                │
    │  显示实时画面                   │                                │
    │                                │                                │
    │ POST .../call/{id}/end         │  poll 收到 call_end             │
    │ ─────────────────────────────► │ ─────────────────────────────► │
    │                                │  停止推流，LED 恢复             │
```

**已验收行为**：

- [x] Web 发起呼叫 → 设备 5s poll 收到 `call_start`
- [x] 设备自动开录（MediaRecorder 路径不变）+ JPEG 预览上传
- [x] AI-screen 轮询 `/frame` 显示画面
- [x] Web 挂断 → 设备收到 `call_end` 并停推流
- [x] 推流中 LED 红绿交替；不影响普通录像/拍照/侧键

**当前妥协**：预览走 **HTTP 中继 + JPEG**，不是真 WebRTC SRTP。目的是先打通指挥链路，再切 NAL/WebRTC。

## 10. 关键设计决策（可能被问到）


| #   | 决策                             | 理由                                      |
| --- | ------------------------------ | --------------------------------------- |
| 1   | SessionManager 编排，platform 做能力 | UI/业务不直接碰 Camera2 或 SIP，降低耦合            |
| 2   | 推流不替代 HTTP 识图                  | `/v1/vision` 仍走拍照 JPEG，与视频流分离           |
| 3   | 信令双轨：MQTT（终态）+ HTTP 中继（当前）     | Web 无需直连 IoT，降低联调门槛                     |
| 4   | 连线时自动开录                        | 未录像则启 V2 管线并开录；已在录像则仅 JPEG 预览（无法中途换编码器） |
| 5   | 录制格式不变                         | MP4/H.264，相册与存储模块零改动                    |
| 6   | 不做的协议                          | RTMP、独立 RTSP、HLS、SRT、H.323              |

## 11. 风险与缓释


| 风险                   | 影响            | 缓释                   |
| -------------------- | ------------- | -------------------- |
| MediaCodec 异步兼容性     | 部分机型编码异常      | 备选 Surface 输入 + 同步模式 |
| PJSIP 体积 +5MB        | APK 增大        | 8GB ROM 可接受          |
| 4G 弱网卡顿              | 预览/推流质量下降     | 动态码率 + FEC（规划）       |
| WebRTC 与 API 29 依赖冲突 | 集成阻塞          | 单独验证 google-webrtc   |
| GB28181 平台未搭建        | 无法 E2E 验收国标链路 | sip-test 模拟 INVITE   |

## 13. 开会讨论议题（建议逐项过）



### A. 优先级确认

1. **P0 先做 NAL 推流还是先做 google-webrtc SDK 集成？**
  - NAL 是 GB28181 和 WebRTC 的共同前置  
  - WebRTC SDK 集成周期不确定，可能阻塞专家连线场景
2. **GB28181 平台由谁提供测试环境？**
  - 代码框架已完成，缺 SIP Server + 平台账号
3. **JPEG 预览链路是否保留为降级方案？**
  - 弱网/联调 fallback vs 维护两套预览路径的成本



### B. 分工与接口

1. **AI-screen Web 端**：谁负责从 JPEG poll 切到 WebRTC js SDK？
2. **MQTT 信令**：何时从 HTTP 中继切到 MQTT 终态？是否需要并行期？
3. **后端 webrtc_signaling**：内存会话是否需持久化/多实例部署方案？



### C. 验收标准

1. **30 分钟推流 + 录制并存**：在什么网络条件下验收？（4G / WiFi / 弱网）
2. **4 路并发**：是 4 台设备各推一路，还是 Web 端 4 画面同屏？
3. **PTT 对讲**：是否纳入 P2 里程碑，还是 V2.1？



### D. 运维与部署

1. **MQTT 三元组**：生产环境配置时间表？
2. **系统签名 + 开机自启**（P4）：是否与 V2 视频并行，还是 V2 验收后再做？
